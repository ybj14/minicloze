# minicloze
A cloze-based language-learning game using the Tatoeba database of sentences plus hand-authored local courses. Written in Rust, with a browser-only static PWA. The name is a reference to the Clozemaster app. This repository contains the Cargo workspace for minicloze.

- **Live web app:** <https://minicloze.vercel.app> (static PWA from `minicloze-web/static`, see [Deploying to Vercel](#deploying-to-vercel))
- **Agent / contributor rules:** [`AGENTS.md`](AGENTS.md) (repository guidelines, data conventions, cache busting) and [`minicloze-lib/corpora/GENERATION_RULES.md`](minicloze-lib/corpora/GENERATION_RULES.md) (binding rules for authoring course sentences). Read both before changing code or corpora.

## Features
- Support for over 400 languages
- Lookup unfamiliar words on Wiktionary
- Support for MacOS, Linux and Windows
- Lean implementation, written in Rust
- High-quality Tibetan word segmentation through Botok
- Local A1 and Swadesh courses with transliteration helpers, word-by-word explanations and SRS scheduling (see [Local courses](#local-courses))
- Offline-capable static PWA, deployable to Vercel or any static host

## Targets
- **Long-term**
- Build a FOSS version of Clozemaster
- **Short-term**
- Learn 100, 1000 etc. most common words of various languages
- Play between two non-English languages

## Installation
To install `minicloze-cli`, the only currently supported frontend, use `cargo install minicloze` (more likely to be up-to-date) or just download a release.

> The crates.io release predates this fork's local courses and web app. To get those, build from this repository (see [Development setup](#development-setup)).

## Tibetan tokenization
Tibetan (`minicloze tibetan`) uses [Botok](https://pypi.org/project/botok/) for word segmentation, [pyewts](https://pypi.org/project/pyewts/) for Wylie transliteration, with learner-facing Tibetan pinyin / 藏文拼音 (ZWPY) for the pronunciation helper line. Install the Python dependencies before playing Tibetan:

```bash
python3 -m pip install botok
python3 -m pip install "setuptools<81" wheel
python3 -m pip install --no-build-isolation pyewts
```

If Botok is installed in a non-default Python, set `MINICLOZE_PYTHON` to that interpreter. For example:

```bash
MINICLOZE_PYTHON=/path/to/python minicloze tibetan
```

For debugging only, `MINICLOZE_TIBETAN_FALLBACK=syllable` falls back to syllable-level splitting when Botok cannot run.

The local `tibetan-a1` corpus can run without Botok by using a built-in target-word fallback. Install Botok and pyewts if you want Wylie plus Tibetan pinyin (ZWPY) helper text.

You can also use the one-step launcher, which runs any language or local corpus. For Tibetan targets such as `tibetan`, `tibetan-a1`, or a future `tibetan-a2`, it creates a local Python environment (`.venv-tibetan`) and installs Botok/pyewts if needed:

```bash
./learn.sh mongolian
./learn.sh tibetan-a1
./learn.sh tajik-a1
./learn.sh thai-a1
./learn.sh tibetan-a1 inverse
```

The older Tibetan-only launcher is still available as a shortcut for `./learn.sh tibetan`:

```bash
./learn-tibetan.sh
```

## Web frontend
The web frontend can run as a static PWA. It loads local corpus JSON directly in
the browser, keeps round state client-side, and can be deployed without the Rust
web server.

Preview the static build locally:

```bash
python3 -m http.server 4173 --directory minicloze-web/static
```

Then open <http://127.0.0.1:4173>. To refresh the static corpus files after
editing `minicloze-lib/corpora`, run:

```bash
./.venv-tibetan/bin/python scripts/build_static_web_data.py

# Mongolian Traditional (Hudum) only (needs npm install):
python3 scripts/build_static_web_data.py --mongolian-only
```

The Traditional Mongolian (bichig) and Poppe lines are machine-generated by `@gege-mn/gege-converter` and are not reviewed by a reader of Traditional Mongolian. Words not covered by a sourced override or a dictionary match (mongoltoli.mn / Wiktionary) are marked `verified: false` in the data and shown with a `*` in the app; see `scripts/data/mongolian_review_queue.md`.

Vercel can deploy the static app from this workspace using `vercel.json`; it has
no install or build command and serves `minicloze-web/static` as the output
directory. The same directory also works on any static host. Details are in
[Deploying to Vercel](#deploying-to-vercel).

You can run the local web version (the Axum server in `minicloze-web/src/main.rs`) in the foreground with Tibetan Wylie support enabled:

```bash
./web.sh
```

For background process control:

```bash
./webctl.sh start
./webctl.sh status
./webctl.sh stop
./webctl.sh restart
./webctl.sh logs
```

The launchers create or reuse `.venv-tibetan`, install Botok and pyewts when needed, and export `MINICLOZE_PYTHON` before starting `minicloze-web`. To choose a different address:

```bash
MINICLOZE_WEB_ADDR=127.0.0.1:4000 ./webctl.sh start
```

An Android shell built with Capacitor lives in [`capacitor/`](capacitor/README.md). It bundles a copy of `minicloze-web/static` and does not change the Vercel deploy.

## Usage
For `minicloze-cli`, just pass in the language (from www.tatoeba.org) you want to use, e.g. `minicloze french`. Add `inverse` for inverse mode (`minicloze french inverse`).

There are also local A1 corpora with original beginner sentences:

```bash
minicloze mongolian-a1
minicloze tibetan-a1
minicloze tajik-a1
```

From a checkout, run the CLI with `cargo run --bin minicloze -- mongolian-a1` (the workspace has two binaries, `minicloze` and `minicloze-web`, so a bare `cargo run` cannot choose one).

Answers can be typed either in the target script or as a Latin transliteration without diacritics. For example, Mongolian `дөрөв` can be answered as `dorov`, and Tibetan `བཀྲ་ཤིས` can be answered as Tibetan pinyin `zha xi` or Wylie `bkra shis`.

### Local courses
These courses are defined in `minicloze-web/static/app.js` (`COURSES`) and `minicloze-lib/src/langs.rs` / `local_corpora.rs`. A1 courses have 500 words × 3 = 1,500 sentences; Swadesh courses have 207 words × 3 = 621 sentences.

| Language | Courses (code) | Helper lines |
| --- | --- | --- |
| Mongolian | `mon-a1`, `mon-swadesh` | Traditional script (bichig) + Poppe romanization, machine-generated with `verified` markers |
| Tibetan | `bod-a1`, `bod-swadesh` | 藏文拼音 (ZWPY) + Wylie |
| Tajik | `tgk-a1`, `tgk-swadesh` | — (Cyrillic) |
| Thai | `tha-a1`, `tha-swadesh` | Paiboon |
| Burmese | `mya-a1`, `mya-swadesh` | MLCTS + Okell |
| Khmer | `khm-a1`, `khm-swadesh` | Wiktionary transliteration + transcription |
| Amharic | `amh-a1`, `amh-swadesh` | Wiktionary Ethi-translit romanization (#9) |
| Armenian | `hye-a1`, `hye-swadesh` | ASCII transliteration |
| Georgian | `kat-a1`, `kat-swadesh` | ASCII transliteration |
| Maltese | `mlt-a1`, `mlt-swadesh` | ASCII-folded learner transliteration (`scripts/maltese_transliteration.py`) |
| Sanskrit | `san-a1`, `san-swadesh`, `san-a1-classical` | IAST (Devanagari targets); Classical rows cite GRETIL sources |

## How to contribute
Any help is very welcome, from humans and from AI agents. Open an issue or a PR. Right now the focus is on expanding from the basic idea into a more fully-fledged and user friendly experience, and on adding accurate courses for less-commonly-taught languages.

[`AGENTS.md`](AGENTS.md) is the detailed rulebook (data conventions, code style, git hygiene). This section is the overview and checklist. When the two disagree, raise it in your PR.

### Repository layout
| Path | What it is |
| --- | --- |
| `minicloze-lib/` | Shared Rust logic: sentence loading, prompts, answer checking, SRS, Tibetan helpers. `src/langs.rs` normalizes language/course aliases; `src/local_corpora.rs` embeds local courses with `include_str!`. |
| `minicloze-lib/corpora/` | **Source of truth** for local courses: `<lang>_<course>.json`, `_vocab.json`, `_explanations.json` (+ `_tokens.json` for Mongolian). `GENERATION_RULES.md` and `README.md` (sources) live here. |
| `minicloze-lib/corpora/generated/` | Reviewed batch JSON (e.g. `maltese_001_050.json`, `sanskrit_swadesh_001_041.json`) that `merge_a1_corpora.py` merges into the corpus files. |
| `minicloze-cli/` | Terminal frontend (binary `minicloze`). |
| `minicloze-web/src/main.rs` | Optional Axum server for local server mode (binary `minicloze-web`). |
| `minicloze-web/static/` | The **deployed static PWA**: `index.html`, `app.js`, `app.css`, `service-worker.js`, `manifest.webmanifest`, `icons/`, `fonts/`, and `data/` (generated mirror of the corpora plus token/transliteration files). |
| `scripts/` | Merge/build/transliteration utilities (`merge_a1_corpora.py`, `build_static_web_data.py`, `mongolian_bichig.mjs`, per-language `*_transliteration.py` / romanizers, course generators) and `scripts/data/` (Mongolian overrides, dictionary evidence and review queue; Sanskrit sources). |
| `capacitor/` | Android shell (see `capacitor/README.md`). |
| `vercel.json` | Static hosting config for Vercel. |
| `package.json` | Node scripts for the Mongolian build/test (`@gege-mn/gege-converter`). |
| `SHIP.md` | Ship notes for the Mongolian bichig/Poppe work, including its review status. |

### Development setup
- **Rust:** a recent stable toolchain via [rustup](https://rustup.rs/) (verified with rustc 1.99.1). Older toolchains may fail to build current dependencies.
- **OpenSSL:** `reqwest` uses native TLS. If `pkg-config` is not installed, point the build at OpenSSL directly, e.g. on Debian/Ubuntu:
  ```bash
  export OPENSSL_LIB_DIR=/usr/lib/x86_64-linux-gnu OPENSSL_INCLUDE_DIR=/usr/include
  ```
- **Python 3** for `scripts/`. The full static-data build needs `pyewts` (Tibetan), which is why it uses `.venv-tibetan`. `./learn.sh tibetan-a1` or `./web.sh` create that venv (via `scripts/tibetan-python-env.sh`).
- **Node.js** (verified with v20) and `npm install` for the Mongolian bichig/Poppe build and tests.

### Adding a new course end-to-end
Use the Maltese PR (#28) and Sanskrit PR (#29) as templates: `git show --stat 48a4451` and `git show --stat 434f270` list every file a new course touches.

1. **Read the rules.** [`minicloze-lib/corpora/GENERATION_RULES.md`](minicloze-lib/corpora/GENERATION_RULES.md) is binding. Write sentences from the meaning and natural usage of each word, three per word. Never fill generic templates in a loop. Scripts may scaffold, validate, merge and enrich, but they must not write the final sentence content.
2. **Vocabulary and sources.** Create `minicloze-lib/corpora/<lang>_a1_vocab.json` (500 items) and/or `<lang>_swadesh_vocab.json` (207 items, seeded from Wiktionary Swadesh data). Newer configs (Maltese, Sanskrit) set `vocab_from_batches` / `explanations_from_batches` and derive these files from the batches in step 4. Record where the word list came from in `minicloze-lib/corpora/README.md` (or a `scripts/data/<lang>/README.md`, as Sanskrit does).
3. **Author batches.** Write reviewed batch files under `minicloze-lib/corpora/generated/`. File names encode the vocab range (`<lang>_001_050.json`, `<lang>_swadesh_001_041.json`, …) and `merge_a1_corpora.py` checks it. Work in batches of about 20–50 words and read each batch as a learner would before merging. Subagent output stays a draft until it has been checked.
4. **Merge and validate.** Add a config entry for the language to `LANGS` in `scripts/merge_a1_corpora.py`: vocab path, output, batch list, a new unused negative `id_start` range, `forbidden` meta-language strings, and, for Swadesh, `expected_count: 207` / `expected_sentences: 621`. Then run:
   ```bash
   python3 scripts/merge_a1_corpora.py <lang> <lang>-swadesh
   ```
   It validates naturalness heuristics, target-word presence, counts and IDs, and writes `minicloze-lib/corpora/<lang>_{a1,swadesh}.json`. Explanations (`*_explanations.json`) must cover every word of every sentence (some configs build them from the batches; see the Sanskrit/Maltese entries and `scripts/generate_full_sentence_explanations.py`).
5. **Transliteration.** For non-Latin scripts, add a standard scholarly or well-established learner transliteration as a `scripts/<lang>_transliteration.py` module and say in its docstring/PR which standard it implements and its source (e.g. Wiktionary module, ALA-LC, IAST).
6. **Build static data.** Add the course prefixes to `COURSE_PREFIXES` (and a `<LANG>_COURSES` list with token/explanation builders, if the language has helper lines) in `scripts/build_static_web_data.py`, then run:
   ```bash
   ./.venv-tibetan/bin/python scripts/build_static_web_data.py   # or: npm run build:static-data
   ```
   This copies the corpora into `minicloze-web/static/data/` and writes `*_tokens.json`. Never hand-edit `minicloze-web/static/data` as the only copy of a change.
   - The full build does **not** currently re-run the Mongolian bichig step (draft PR #27 addresses this). If you touched Mongolian data, also run `npm install && npm run build:static-data:mongolian && npm run test:mongolian`.
7. **Wire the course in.** Edit these together:
   - `minicloze-lib/src/langs.rs`: display name / aliases (`<lang>-a1`, `<code>-a1`, …) and the alias→code tests.
   - `minicloze-lib/src/local_corpora.rs`: `include_str!` entries for the corpus, vocab and explanations.
   - `minicloze-web/static/app.js`: a `COURSES` entry (`code`, `label`, `slug`, `baseLanguage`, `sentenceCount`, `corpusPath`, `vocabularyPath`, `explanationsPath`, `tokensPath`, all via `dataPath(...)`) plus any rendering for new helper fields.
8. **Bump the caches** (see [Cache busting](#cache-busting)): `DATA_VERSION` in `app.js`, the `?v=` asset strings in `index.html` and `service-worker.js`, and `CACHE_NAME` in `service-worker.js`.
9. **Test** (see below), preview the static app locally, and play a few rounds in multiple-choice, text-input and inverse modes.
10. **Open a PR** to `master` with a summary, the sources used, the validation you ran, and anything that is still unverified.

### Quality bar
minicloze teaches real languages, so content accuracy matters more than coverage.
- **Scholarly accuracy.** Sentences must be natural and grammatical, and translations must be faithful. Odd sentences like "Who is the book?" count as failures even when every schema check passes (see `GENERATION_RULES.md` and `AGENTS.md` → Data Conventions).
- **Scripts and transliterations must be sourced.** Every non-trivial script conversion, transliteration scheme, or lexical override needs a citable source (dictionary, Wiktionary module, published standard, primary text). Examples in the repo: Khmer follows Wiktionary `Module:km-pron` (#2), Amharic ports Wiktionary Ethi-translit (#9), Sanskrit Classical rows carry `citation` / `source_text` pointing at GRETIL lines (#29), and Mongolian fixes go only through source-cited rows in `scripts/data/mongolian_bichig_overrides.json`.
- **Generated output is not "verified".** Output from an LLM, a converter, or a script is a draft. Do not describe it as reviewed, verified, or "matching" a standard unless someone actually checked it against a source. The precedent is the Mongolian bichig/Poppe line (#30, [`SHIP.md`](SHIP.md)): every word carries `verified: true|false`, where `true` means "sourced override or dictionary-checked" (still not human-reviewed), unverified words show a `*` in the app, and open items are listed in `scripts/data/mongolian_review_queue.md`. An earlier claim that the romanization "matched Poppe conventions" turned out to be false and had to be corrected. If you can't verify something, mark it and say so in the PR.
- **Don't normalize away non-ASCII text** (tseks, Thai spelling, Cyrillic, transliteration fields), and keep each course's negative `id_start` range stable.

### Testing
Run from the repository root:

```bash
cargo fmt                                   # needs the rustfmt component: rustup component add rustfmt
cargo test                                  # all Rust tests (aliases, corpus/explanation alignment, SRS, answer checks, web options)
npm install && npm run test:mongolian       # Mongolian bichig/Poppe regression tests (node --test scripts/test_mongolian_poppe.mjs)
python3 scripts/merge_a1_corpora.py <lang>  # corpus validation for the language you changed (rewrites its corpus JSON)
python3 -m http.server 4173 --directory minicloze-web/static   # manual check at http://127.0.0.1:4173
```

Notes:
- `cargo test` needs a recent stable Rust toolchain and OpenSSL (set `OPENSSL_LIB_DIR` / `OPENSSL_INCLUDE_DIR` if there is no `pkg-config`, see [Development setup](#development-setup)). Run it after rebuilding static data too, since it checks the corpora embedded by `local_corpora.rs`.
- If you change a Python/Node generator, run it on the affected language and inspect the JSON diff (`git diff --stat`, plus samples).
- There is no CI in this repository (no `.github/workflows`). Include the commands you ran and their results in the PR description.

The `package.json` scripts that exist today are `build:static-data`, `build:static-data:mongolian`, `build:mongolian-bichig` and `test:mongolian`.

### Branches, PRs and merging
- Work on a feature branch off an up-to-date `master`. Branch names in this repo follow `feat/…`, `fix/…`, `rewrite/…`, `docs/…` (e.g. `feat/sanskrit-a1-swadesh`, `fix/mongolian-poppe-review`).
- Open a PR **to `master`**. Keep one topic per PR (one course, one fix). Large generated-data diffs are expected for courses, so call out the hand-written parts in the description.
- PRs are **squash-merged** (every merge on `master` is a single `… (#N)` commit).
- **The owner (ybj14) decides what gets merged.** AI agents and bots must not merge PRs, push to `master`, force-push someone else's branch, or rewrite `master` history. Push your own feature branch and open a PR (a draft if it is not ready), then leave the merge to the owner.
- Don't commit runtime artifacts: `target/`, `node_modules/`, `.venv-tibetan/`, `.minicloze-web.log`, `.minicloze-web.pid`, `.DS_Store`, `__pycache__/`.

## Deploying to Vercel
### How the deploy works
- [`vercel.json`](vercel.json) sets `"framework": null`, `"installCommand": null`, `"buildCommand": null` and `"outputDirectory": "minicloze-web/static"`. Vercel runs **no build**. It serves the committed contents of `minicloze-web/static` as-is, with `cleanUrls: true`. Data files must be **built locally and committed**. Nothing is generated on Vercel.
- Cache headers from `vercel.json`:
  - `/`, `/index.html`, `/service-worker.js`, `/manifest.webmanifest`: `no-cache, max-age=0`
  - `/data/*` and `/icons/*`: `public, max-age=31536000, immutable` (one year). **A changed data file is only picked up when its URL changes**, which is what `DATA_VERSION` is for.
- Production is <https://minicloze.vercel.app>. It responds with `server: Vercel`, and on 2026-11-03 it served the same asset version (`static-pwa-20261031-01`) as `master`.
- *Assumed, not visible in the repo:* the Vercel project is connected to GitHub through Vercel's Git integration, so pushes to `master` deploy to production and PR branches get preview deployments. The repo has no Vercel CLI config or GitHub workflow, and the project link and its settings live in the Vercel dashboard (owner only). Ask the owner if you need a preview URL or deploy logs.

### Local preview
```bash
python3 -m http.server 4173 --directory minicloze-web/static
# open http://127.0.0.1:4173
```
This serves the same files Vercel serves (without the `vercel.json` headers). The service worker caches aggressively, so use a private window or DevTools → Application → "Update on reload" / "Clear storage" when testing changes.

### Cache busting
Whenever you change `app.js`, `app.css`, `index.html`, service-worker behaviour, or anything in `static/data/`, bump all of these in the same commit:

| Where | What | Current example |
| --- | --- | --- |
| `minicloze-web/static/app.js` | `DATA_VERSION` (appended as `?v=` to every `/data/*.json` URL via `dataPath`) | `static-data-20261030-1` |
| `minicloze-web/static/index.html` | `?v=` on `/app.css` and `/app.js` | `static-pwa-20261031-01` |
| `minicloze-web/static/service-worker.js` | the same `?v=` strings in `APP_SHELL` | `static-pwa-20261031-01` |
| `minicloze-web/static/service-worker.js` | `CACHE_NAME` (increment; old caches are deleted on activate) | `minicloze-static-pwa-v45` |

Convention from history: `static-data-YYYYMMDD-N`, `static-pwa-YYYYMMDD-NN`, and `vN+1` for `CACHE_NAME`. The new service worker waits until the user taps the in-app **Update** toast (#20).

### Verifying a deploy
After the owner merges (or on a preview URL), check:

```bash
BASE=https://minicloze.vercel.app   # or the preview URL

# 1. The page serves the new asset version (should match index.html on master)
curl -s "$BASE/" | grep -o 'static-pwa-[0-9-]*' | sort -u

# 2. The service worker and data version are the new ones
curl -s "$BASE/service-worker.js" | head -1      # const CACHE_NAME = "minicloze-static-pwa-vNN";
curl -s "$BASE/app.js" | head -1                 # const DATA_VERSION = "static-data-...";

# 3. Every course file returns 200 (replace with your course prefix)
```

### Troubleshooting
- **Old UI or old data after deploy:** a cache value was not bumped (see the table above), or the browser is still on the old service worker. Tap Update or reload twice. `/data/*` is cached as immutable for a year, so a data change without a new `DATA_VERSION` can stay stale.
- **`404` on `/data/<course>.json`:** the file was not committed under `minicloze-web/static/data/`, or the path in `COURSES` is wrong. Re-run `build_static_web_data.py` and check `git status`.
- **`503` with the body "Offline — this resource is not cached yet.":** this comes from the service worker (`networkFirst` / `staleWhileRevalidate`), not from Vercel. The network request failed and nothing was cached.
- **A transient `503` (or other 5xx) straight from Vercel** (no service worker involved, e.g. via `curl`): this has been seen as a Vercel-side hiccup. Retry after a minute before debugging the repo. If it persists, the owner needs to check the Vercel dashboard.
- **The deploy did not change at all:** Vercel serves only what is committed on the deployed branch. Make sure the data files and version bumps are in the merged commit.
